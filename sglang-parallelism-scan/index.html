sgl-cookbook 扫描：什么模型、什么场景，该用什么并行

扫描对象：sgl-project/sgl-cookbook @ 7b5bd9c（2026-08-31 拉取）。

三个数据源，互相并不完全一致（见第 5 节）：

来源 内容 规模
data/models/generated/*/*.yaml 每个 (模型 x 硬件 x 具名配置) 的 tp/dp/ep/dp-attention 538 行，121 个模型，11 种硬件
docs/**/*.md 每个模型的启动命令、配置建议、benchmark 78 篇
data/optimal-configs/src/v0.5.6/deepseek-r1.yaml 唯一一份「调优过」的场景矩阵 1 个模型

cookbook 里没有一章讲「并行选型原理」。 docs/base/reference/server_arguments.md 只有 16 行，是个参数名对照表。 所以下面的规则是我从 538 条配置里反推出来的，不是它写好的。

1. 它自己的场景分类

optimization 字段只有三个值，配置名也就那几种：

optimization 配置名 数量 开 DP attention 的比例
balanced default 376 0 / 376
low-latency speculative-mtp / speculative-eagle(3) / latency-optimized 87 0 / 87
high-throughput high-throughput-dp / high-throughput-ep / throughput-optimized 75 48 / 75

没有任何一条 low-latency 或 balanced 配置开 DP attention。 EP 也一样：low-latency 里 87 条只有 1 条设了 ep。

GLM-5 的文档把这条规则用大白话写出来了（docs/autoregressive/GLM/GLM-5.md §3.2）：

DP Attention: Enables data parallel attention for higher throughput under high concurrency. Note that DP attention trades off low-concurrency latency for high-concurrency throughput — disable it if your workload is latency-sensitive with few concurrent requests.

2. 同一个模型、同一批卡，两种场景的完整对照

docs/autoregressive/DeepSeek/DeepSeek-V3_2.md §5.1 是最干净的一组，B200 8 卡，同模型：

启动参数 并发 总吞吐
Latency-Sensitive --tp 8 + EAGLE(3 步) 1 163.36 tok/s
Throughput-Sensitive --tp 8 --ep 8 --dp 8 --enable-dp-attention 100 2236.86 tok/s

低并发那档：纯 TP，不开 dp，不开 ep，改用投机解码去压延迟。 高并发那档：tp / ep / dp 三个都开满。

3. 按模型族的规则

3.1 拿到 high-throughput-dp 配方的模型（18 个）

全部集中在四个族：DeepSeek（V3.2 / R1 / Math-V2）、GLM（4.6 / 5 / 5.1）、Kimi-K2（K2 / K2.5 / K2.6）。

架构核对（各自 HF config.json）：

模型 attention KV head expert tp8 下会不会复制 KV
DeepSeek-V3/R1/V3.2 MLA（kv_lora_rank 512 + rope 64） 1 个 latent 256 会，复制 8 份
Kimi-K2.x MLA（DeepseekV3ForCausalLM） 1 个 latent 384 会，复制 8 份
GLM-4.5 / 4.6 GQA，8 个 KV head，96 个 q head 8 160 tp8 刚好整除，不复制

这里有个值得注意的点：GLM-4.6 在 tp8 下并不复制 KV，却照样给了 DP attention 配方。 所以 DP attention 的动机不止「省 KV 复制」一条——GLM 这种情况省的是每张卡把全部 token 的 RMSNorm / router 重算一遍的冗余，以及 attention 段的 all-reduce。 不过 GLM-5 的硬件表写着 H100 FP8 要 tp=16，到那个宽度 8 个 KV head 就开始复制 2 份了。

3.2 只给 EP、不给 DP attention 的模型

Qwen3-235B-A22B-FP8（含 VL / Thinking 变体）、Qwen3.5-397B-A17B、Step-3.5-Flash、Intern-S1。

Qwen3-235B 的官方配置只有一条：tp=8, ep=2, balanced，没有任何 high-throughput 配方。 ep=2 意味着 moe_tp_size = 8/2 = 4，moe_intermediate_size 1536/4 = 384，满足 fp8 blockscale GEMM 的 N % 64 == 0。

3.3 dense 模型

default tp=1 出现 190 次——绝大多数模型（Llama / Mistral / Gemma / Qwen dense / 各种 VL） 的官方答案就是单卡或窄 TP，没有任何 dp / ep。

4. 硬件与跨节点

4.1 TP 宽度是显存的函数

GLM-5 文档给的表最直白：

硬件 FP8 BF16
H100 tp=16 tp=32
H200 tp=8 tp=16
B200 tp=8 tp=16
MI300X / MI325X / MI355X — tp=8

它同时写了一句通则：BF16 在 NVIDIA 上永远要 FP8 的 2 倍卡。

各硬件 default 配置的 tp 分布也印证了：H100 上出现 tp16 / tp32，H200 / B200 上同样的模型只要 tp8， AMD（192 GB）上大量模型 tp4 就够。

4.2 超过一个节点：用 PP，不是把 TP 拉宽

docs/autoregressive/InclusionAI/Ling-2.5-1T.md：

--tp-size can be set to a maximum of 8 for this model. If you have more GPUs available, increase --pp-size to scale across additional nodes.

data/models/generated 里 538 条全部是 nodes: single，跨节点的例子只在 markdown 里， 而且用的都是 --nnodes 2 --pp-size 2。

4.3 CP 出现的唯一场合

整个 cookbook 里 CP 只在 DeepSeek-V3.2 的 §4.2.3 出现，而且是 NSA 专用开关 （--enable-nsa-prefill-context-parallel，配 --nsa-prefill-cp-mode round-robin-split）， 跟 --pp-size 2 一起用。没有任何 --dcp-size 的例子。

4.4 DP 宽度不是越大越好（cookbook 自带的实测）

DeepSeek-V3.2 §4.2.3 注释里留了一组 Hopper 2 节点 tp16 的 ISL/OSL=1k/1k 数据：

配置 吞吐 MAX ITL
不开 dp 4948.16 tok/s 5970
dp 2 5019.54 tok/s 7233
dp 4 4942.82 tok/s 35654
dp 2 + MTP 6842.51 tok/s 3081

dp 从 2 加到 4，吞吐反而掉回不开 dp 的水平，尾延迟涨了 5 倍。 官方推荐停在 dp2 + MTP。

5. 三处不一致 / 疑似 bug

5.1 9 条配置 dp > tp，起服会直接 assert 失败

模型 硬件 配置 tp dp
Kimi-K2.6 MI300X / MI325X / MI350X / MI355X high-throughput-dp 4 8
Kimi-K2.5 MI300X / MI325X / MI350X / MI355X high-throughput-dp 4 8
GLM-5-NVFP4 B200 high-throughput-dp 4 8

成因在源 YAML：high-throughput-dp 这个配置块写在文件级、硬编码 dp: 8， 而 tp 是每个硬件各写各的（H200/B300 是 8，AMD 系是 4）。两边没有联动。

sglang 侧会拒绝：arg_groups/parallel_hook.py 在 enable_dp_attention 解析为真时有一条 无条件的 assert cfg.tp_size % cfg.dp_size == 0。4 % 8 = 4，直接 AssertionError。 （另外 compute_world_size 在开 dp attention 时返回 tp_size * pp_size = 4，也和 dp=8 对不上。）

5.2 同一个模型，两份数据给的答案不同

DeepSeek-R1-0528 在 H200 上：

  • data/models/generated/v0.5.6/deepseek-r1.yaml：high-throughput = tp8 + dp8 + enable_dp_attention
  • data/optimal-configs/src/v0.5.6/deepseek-r1.yaml：high-throughput = tp8，不开 dp，不开 ep

后者是唯一一份标称「pre-tuned, benchmarked」的文件，它里面 low-latency 和 high-throughput 的 并行参数完全相同，两档的差别只有 scheduler_recv_interval（10 vs 30）和 stream_interval。

5.3 DP 和 EP 是「二选一」还是「一起开」，两处也不一样

data/models/generated 把它们拆成两个互斥配方（high-throughput-dp 里 ep 恒为空， high-throughput-ep 里 dp-attention 恒为空）； 而 docs/.../DeepSeek-V3_2.md §5.1.2 的吞吐 benchmark 是 --tp 8 --ep 8 --dp 8 --enable-dp-attention， 三个一起开。
