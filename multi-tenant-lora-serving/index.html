Paper → kernel → runtime → cluster

Multi-tenant LoRA Serving

从共享一份 base model，到让成千上万个 adapter 真正共享 GPU：一段由算子、显存、调度与路由共同推动的系统演化史。

短答：是，已经搞了很久。 2021 年 LoRA 给出算法前提，2022 年 PetS 已经在做 parameter-efficient 多任务 serving；真正围绕 LoRA 的系统爆发发生在 2023–2024 年。此后问题不再只是“怎么把 LoRA 跑起来”，而是“怎么在异构、突发、跨 GPU 的真实租户流量里守住 P99 和成本”。
5 layers kernel · memory · scheduler · router · isolation
少任何一层，都更像 demo 而不是 multi-tenant system。
01 / 原点

LoRA 很小，租户问题很大

LoRA 的算法形式天然适合共享：大矩阵 W 冻结，每个任务只带一对低秩矩阵。但推理一旦混入不同 adapter，原本规则的 dense batch 就被切碎了。

y = Wx + BᵢAᵢx
W：所有租户共享 Aᵢ / Bᵢ：租户 i 私有 i：随 request 改变
单个 adapter 可以先 merge 进 W，推理几乎没有额外路径；但多个 adapter 同时服务时，merge 会复制/改写大模型权重，失去共享的意义。系统于是选择保持 unmerged，在每层为不同 token 执行不同的低秩分支。LoRA 论文奠定了这个结构，multi-tenant serving 则接手了它的运行时后果。[1]
Compute

batch 不再同质

同一个 decode step 里的 token 可能属于不同 adapter。逐 adapter 启动小 kernel 会导致 launch overhead 和低利用率。

Memory

小权重也会爆

adapter 数量远大于活跃数量；rank、target modules、dtype 还可能不同。需要 CPU/GPU 分层缓存与驱逐。

Policy

谁先跑是系统问题

热 adapter、冷 adapter、长短请求、不同租户 SLO 相互干扰。调度要同时看 locality、公平性与 tail latency。

02 / 时间线

六年里，瓶颈一层层外移

这条历史不是“后一个系统替代前一个”，而是关注点从模型表示，依次推到 kernel、显存、单机调度，再推到整个 replica fleet。

2021–22
Share parameters

LoRA 与 PetS：先证明“共享 backbone”值得做

LoRA 把任务差异压缩为低秩更新；USENIX ATC’22 的 PetS 则更早从系统角度统一 Adapter、Prefix/Prompt Tuning、BitFit 等 PET 任务，把共享算子与任务私有算子拆开，并让不同任务可以共同 batching。它还不是今天专门的 LoRA runtime，但已经提出了核心系统命题。[1][2]

时代关键词：从“一任务一模型”改成“一 backbone，多任务增量”。

2023
Batch heterogeneity

Punica：用 SGMV 把不同 adapter 放回同一个 batch

Punica 的关键贡献是 Segmented Gather Matrix-Vector Multiplication：按 adapter 把 token 视作不同 segment，在一次 batched kernel 中执行各自的低秩矩阵运算。它还用 scheduler 将多租户工作负载合并进共享 GPU cluster；论文报告相对当时基线最高 12× 吞吐提升、每 token 约 2ms 额外延迟。[3]

时代关键词：不是只共享权重，还要共享一次 GPU launch。

2023–24
Page everything

S-LoRA：把 adapter 和 KV cache 一起分页

S-LoRA 将所有 adapter 保留在 host memory，只把当前活跃的部分搬到 GPU。Unified Paging 用统一内存池同时管理不同 rank 的 adapter weights 与不同长度的 KV tensors，避免预留大块连续空间造成碎片；配合定制 kernel 与 tensor parallelism，把目标从“几十个”推到“数千个 adapter”。论文报告最高 4× 吞吐提升。[4]

时代关键词：adapter catalog 可以无限大，GPU working set 必须有限。

2023–24
Productize

LoRAX 与 TGI：把论文能力变成动态 adapter exchange

Predibase 的 LoRAX 从 TGI 分叉，组合了异构 continuous batching、SGMV、GPU/CPU 分层缓存、异步 prefetch/offload、OpenAI-compatible API、可观测性和私有 adapter 隔离。它说明生产系统的难点不止 kernel：adapter 从对象存储到 RAM 再到 VRAM 的生命周期，本身就是 data plane。Hugging Face TGI 随后也提供多 LoRA 预加载与异构 batch。[5][6]

时代关键词：从 benchmark engine 走向可部署 runtime。

2024
Choose the mode

dLoRA：merged 与 unmerged，不必二选一

dLoRA 观察到流量若高度偏向少数 adapter，直接 merge 可能比异构低秩 kernel 更划算；流量分散时则相反。它用 credit-based batching 动态 merge/unmerge，并把 request 与 adapter 在 replicas 间共同迁移，处理自回归长度差异导致的负载不均。OSDI’24 论文报告对 vLLM / PEFT 基线最高 57.9× / 26× 吞吐提升，并比 S-LoRA 最多降低 1.8× 平均延迟。[7]

时代关键词：execution mode 也成为在线调度决策。

2024–25
Protect the tail

CaraServe 与 Chameleon：开始正面解决冷启动、rank 与 P99

CaraServe 在 adapter 还从内存搬向 GPU 时，先用 CPU 执行 prefill，加载完成再切回 GPU，并以 rank-aware scheduling 提升 SLO attainment。Chameleon 则用 popularity-aware GPU cache 和非抢占多队列调度，避免 cache miss 与 head-of-line blocking；论文报告高负载下 P99 TTFT 降低 80.7%。[8][9]

时代关键词：平均吞吐不够，cold path 与 tail 才决定产品体验。

2024–26
Mainstream stack

vLLM、SGLang、Ray Serve：能力下沉到通用推理栈

vLLM 已支持请求级 adapter、动态 load/unload、LoRA resolver 与 tensor-parallel 选项；SGLang 提供 Triton / chunked-SGMV backend、动态加载、GPU pinning、LRU/FIFO eviction；Ray Serve LLM 再往上一层做 adapter-aware replica routing 与每副本 LRU cache。multi-LoRA 从独立研究系统，变成 serving engine 与 cluster controller 的标准能力。[10][11][12]

时代关键词：单机 kernel 问题变成全栈 locality 问题。

03 / 系统视角

今天的 multi-tenant LoRA，是五层协同

把“支持 LoRA”写进 feature list 很容易。真正的 multi-tenant serving 要让同一个 adapter ID 从 API 一直贯穿到 GPU kernel，而且每一层都理解 locality 与隔离。

L5 API
身份、权限与版本tenant → adapter 映射，版本固定，鉴权、配额与审计。论文通常从这里往下看，生产系统不能。
L4 Route
adapter-aware routing优先去已经缓存该 adapter 且负载合适的 replica；否则决定在哪里触发 cold load。
L3 Sched
continuous batching按 token 迭代重组 batch，同时权衡 adapter locality、rank、请求长度、公平性和 SLO。
L2 Memory
分层缓存与 paging对象存储 / 磁盘 → host RAM → pinned memory → VRAM；adapter 与 KV cache 竞争同一块珍贵显存。
L1 Kernel
SGMV / BGMV / GEMMbase 路径照常做 dense GEMM；adapter 路径将异构 token 映射到正确 A/B weights，避免碎 kernel。

命中热 adapter 时，链路看起来近似普通 vLLM 请求；cache miss 时，权重获取、校验、搬运、调度等待都会出现在 TTFT 尾部。

Merge 还是 unmerged？
热点集中、驻留稳定时 merge 有吸引力；长尾且并发异构时保持低秩分支更适合共享。
按请求还是按 token batch？
自回归生成长短不一，continuous batching 必须在每个 step 更新 adapter 映射。
cache 什么？
不仅 cache adapter 文件，还要考虑转换后的 layout、GPU buffer、CUDA graph 与 KV prefix。
路由看什么？
只看 replica queue 会牺牲 adapter locality；只看 locality 又可能把热点压到一张卡。
最容易被混淆的一点：“multi-LoRA kernel”解决的是一个 batch 内不同 adapter 的计算；“multi-tenant serving”还必须解决 catalog、cache、routing、SLO 和安全边界。前者是必要条件，不是完整答案。

06 / 今天怎么看

四个已经清楚、但还没完全解决的事实

01. adapter locality 与 KV locality 会打架

把请求送到有 adapter 的 replica，未必命中它的 prefix KV；反过来也一样。两个 cache 的联合路由仍是开放的策略空间。

02. rank 是资源维度，不只是训练超参

不同 rank 改变权重大小、kernel shape、预留 buffer 与执行时间。为了“兼容最大 rank”而统一预分配，可能浪费大量显存。

03. 运行时动态加载本身就是安全接口

adapter path、远端下载、tenant 映射和版本替换都扩大攻击面。vLLM 文档明确提醒动态 load/unload 不应直接暴露在非受信环境。[10]

04. “千 adapter”不等于“千 adapter 同时活跃”

大 catalog 通常驻留在 host 或对象存储，VRAM 只装 working set。论文的规模数字必须和活跃并发、cache hit rate、rank 分布一起看。

Yes.

所以，这件事确实搞了很久。

但它并没有“被一个 paper 解决”。算法让权重可共享，Punica 让异构 adapter 可同批，S-LoRA 让内存可扩展，LoRAX 把交换流程产品化，dLoRA / CaraServe / Chameleon 把在线决策与尾延迟拉进来，vLLM / SGLang / Ray 再把这些能力拆进通用 engine 与 cluster layer。

multi-tenant LoRA 的变迁，本质上是边界持续外移：从矩阵分解，到 kernel；从 kernel，到 memory；从 memory，到 scheduler；最后到 routing、SLO 与隔离。今天最值得做的，已经不是再证明 LoRA 可以共享，而是把这五层做成一个可观测、可控、可演进的系统。
