持续学习 · 落地计划

把持续学习的循环接上部署和进化都已就绪，缺的是起点：没有人把真实工作变成训练数据。这是补上那一环的计划。

一个 agent 要在同一个环境里反复干活，理想状态是它从每次经验里积累对这个环境的认识。实现这件事的框架已经存在：可移植的 harness adapter、沙箱隔离的进化会话、候选产物与人工评审。但整条链在最左端是断的——没有任何东西负责把"agent 实际干了什么"变成可供学习的记录。本文是补上这一环的具体计划，以及补完之后用户看到的形态。

2026-10-03 · 计划文档，非实现报告 · 三件中已完成一件

一句话：缺的不是工程量，是一个输入。进化需要"带判定的记录"，而真实使用中没有人产生它。

解法：用 Claude Code 的 mod 在会话内部记录 episode，并把判定来源分三档可信度写进记录本身。

1 · 断在哪里

把这套东西类比成模型训练，对应关系相当整齐：

模型训练这里状态
模型结构adapter 的起始布局有
训练出来的权重adapter：学到的 prompt、知识、工具、角色有
训练算法Evolver有
推理部署到 host有
训练数据录下来的 episode没有人产生

前四行都已经实现得相当扎实。第五行是空的——不是没做好，是整个采集环节不在框架的职责范围内。它的设计假设是：谁用它，谁负责提供数据。

这个假设在 benchmark 里成立：benchmark 自带判分器，每道题的对错是免费的。在真实工作里不成立——没有人告诉你 agent 这次干得对不对。

所以"用户边用我们边收集"这个直觉，只对了一半。轨迹好拿（会话里什么都看得见），标签没地方来。这是整件事唯一的硬骨头，其余都是工程。

3 · 记录器（关键的一件）

Claude Code 的 mod 跑在它自己的进程里，能看见会话的全部事件。挂三个 hook 就够：

on('turn.complete', ...)   // 这一轮要做什么、做完了什么
on('tool.call', ...)       // 调了哪些工具、返回了什么
on('session.append', ...)  // 每条被留存的记录

写出来是一个普通目录，一条记录一个文件：

{
  "id":         "稳定地址，被引用时用它",
  "task":       "要干什么",
  "did":        "实际做了什么",
  "outcome":    "环境用它自己的话返回了什么",
  "verdict":    "right | wrong | undetermined",
  "checked_by": "这个 verdict 是谁给的",
  "note":       "为什么"
}
checked_by 是刻意加的字段。它把"标签从哪来"写进记录本身，让后续的学习者自己判断这条证据有多硬——而不是把所有 verdict 一视同仁。

4 · verdict 的三档

不猜。按可信度分三档，每一档都在 checked_by 里留痕：

档位怎么拿checked_by可信度
机械判据配一条验证命令（测试、构建、lint），看退出码"exit code of <cmd>"最高
用户显式标/mark right|wrong [理由]"human"中
默认什么信号都没有"undetermined"—

默认写 undetermined 而不是猜。这不是保守，是必需：一条被当成"已验证"的错误结论，比一条诚实的"还不确定"有害得多。方法本身也要求区分"已验证的事实"和"当前的工作默认值"。

一个真实的反面教材。某个评测装置把工具输出截断在 800 字符，而被评测的环境本身不截断。于是干活的 agent 看到完整响应，学习者只看到一半。学习者把截断归因于环境，写下"关键信息在 800 字符上限之外"，然后连续八轮记录"是这个上限而不是我的推理限制了结论"。

一个没写文档的管道参数，让学习者连着八轮得出系统性错误的结论——而且它的推理过程看起来完全合理。证据管道上的每一处加工都必须对学习者可见。

5 · plugin 部署目标

现有的部署产出和 Claude Code plugin 的布局差得不多：

现在写出的：  项目指令文件   MCP 配置   原生子 agent 定义
plugin 要的： skills/        MCP 配置   agents/   + 一份 manifest

加一个 connector 即可，跟现有的并列。好处是直接解决"只能生成独立 workspace、无法合并进已有项目设置"这个已知限制——plugin 本身就是那个合并机制。

但 adapter 本身必须保持 host 中立。harness adapter 的全部意义是一份产物能部署到不同的 agent 产品。如果最终产出直接就是某一家的 plugin 格式，可移植性就没了，"adapter"这个概念也就没了。plugin 是第三个出口，不是产物格式。

6 · /evolve 命令

已完成

一个 mod 注册 /evolve，把进化会话作为独立进程拉起来，然后轮询结果。

为什么进化本身不能跑在 mod 里：mod 的 hook 单事件只有 10 秒预算，而一轮进化要几分钟到半小时；更重要的是 mod 不在沙箱里，而整个进化流程的严谨性恰恰建立在 OS 级隔离上。所以 mod 只做扳机，进化留在外面——沙箱完整保留。

实现上有两个坑值得记下来：

  • 不能用流式的 spawn 接口 fire-and-forget——它是异步生成器，不消费流进程就不会跑完。改成通过 shell 后台化，启动调用立刻返回，进程完全独立于会话。
  • 轮询会和框架写文件撞上——读到半个 JSON 必须不抛异常，下一个周期再试。这条有测试覆盖。

7 · 最终的用户形态

装两个东西

/plugin install evolve-kit@<源>      # 稳定：/evolve + 自动记录
/plugin install my-adapter@<源>      # 数据：学到的东西，每轮换版本

拆成两个是因为生命周期不同：trigger 基本不变，adapter 每轮都变。捆在一起意味着每出一个候选都要重发 trigger 的代码，而且会变成"一个运行中的插件热替换自己"。

平时：什么都不用做

正常干活。记录在后台进行——不打断、不起新对话、不要求用户做任何事。偶尔标一下：

> /mark wrong 这次漏了必填的参数

配了验证命令的项目连这步都省——退出码自动当标签。

想学一轮：敲一个命令

> /evolve

● evolve-kit
  Evolution session started. Nothing is adopted automatically.

prompt 下方出现一行常驻状态。不阻塞，用户继续干活。几分钟后状态更新，transcript 里多一行暗色结果，右上角弹一个提示。

采用：人来决定

cat  <session>/control/report.md     # 学习者自己写的报告
git -C <session>/adapter log -p      # 它到底改了什么

觉得行再发版、更新插件。没有任何东西自动上线。

整条链路

正常工作 ──(自动记录)──> LearningMaterial
                              │
                         /evolve（手动）
                              │
                   候选 adapter（带完整 git 历史）
                              │
                          人 review
                              │
                    更新插件 / 部署到别的 host

跟今天的区别只有一处，但它是决定性的：左边那个"自动记录"。没有它，这条链在起点就断了。

8 · 刻意不做的

  • 自动晋升。评审是唯一挡在"学歪了"和"上线"之间的东西。候选的状态标记只表示"跑完了且结构检查通过"，不表示效果变好——自动采用等于把这个区别抹掉。
  • 把进化搬进宿主进程。省掉的是一个子进程，丢掉的是 OS 级隔离。不划算。
  • 猜测 verdict。宁可标 undetermined。
  • 追求通用。见下。

9 · 仍未解决的

可验证场景之外，verdict 没有好来源。

机械判据只在有客观判据的地方成立：测试过没过、命令退出码、环境明确报错。写代码、跑集群作业、调用有明确契约的 API——这些都够用。

但"这段文案写得好不好""这个设计合不合理"这类，没有机械判据。可选的替代品各有问题：隐式信号（有没有被 revert）噪声大且"没被 revert"不等于"对"；模型评判有偏、可被刷，而且违反"只写能对照环境判定对错的东西"这条准入原则。

所以建议先只在可验证场景用，不要追求通用。窄，但标签免费且干净。一个在窄场景里真的有效的循环，比一个在宽场景里产出可疑结论的循环有价值得多。
