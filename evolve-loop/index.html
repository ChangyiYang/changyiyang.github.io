产品定义 · 用户切面

会积累经验的编码助手

助手在每个 turn 的边界上积累材料。用户在需要的时候产出一个 mod、装上、之后更新。不新造任何机制——产出物本身就是宿主已经认识的东西。

2026-10-03 · 只定义用户切面

0 · 核心：不在旁边包一层

这套东西已经有一组完整的概念：一份可移植的经验（里面有知识、工具、角色），加上"从材料里产出下一版"这个动作。

要做的是让这些概念落进宿主已有的东西里，而不是在旁边平行造一套。

这套 API 里的落进宿主就是
经验里的工具插件自带的工具服务
经验里的角色插件自带的子 agent
经验里的知识插件目录里的文件
经验的上下文每个会话开头注入
积累材料turn 边界上的钩子
产出下一版一个命令
装上 / 换版本宿主本来就有
最后一行是关键：没有"部署"这一步。产出物就是一个插件，装它用宿主自带的装插件方式。我们不写安装、不写更新、不写回滚——那些宿主已经做好了。

所以最终是一个插件装着全部东西：

一个插件
├── 钩子        记录 + 注入上下文 + 提供产出命令
├── 工具服务    经验里的工具
├── 子 agent    经验里的角色
└── 知识文件

产出下一版，就是产出这个插件的下一版。

1 · 平时做什么

在每个 turn 的边界上积累材料。开始时记下要做什么，结束时记下做了什么、环境返回了什么、成没成。中间的工具调用、报错、重试都在这些边界上留痕。

没有命令。不需要开启、不需要确认、不需要标注。

零打扰是硬约束。任何需要用户"配合一下"的记录机制，最后都会被关掉。

2 · 用户如何

2.1 产出

> /evolve

  从积累的材料里提炼中…（不阻塞，可以继续干活）
  ✓ 产出 v2 — 看看它学到了什么再决定装不装

第一次运行时从空白开始；之后自动以当前装着的那版为起点，所以用户两次敲的是同一个命令。

产出不自动生效，先给人看。

2.2 安装

用宿主自带的装插件方式。可以装自己产出的，也可以装别人产出的——经验是可分享的。

一个项目一份，换项目换一份，互不污染。

2.3 更新

同样是 /evolve——它已经以当前版为起点，所以产出和更新是同一个动作，不需要第二个命令。

换到新版、退回旧版，都用宿主自带的方式。旧版本身没被改动过，所以回滚就是继续用它。

3 · 用户要学的新东西：一个命令

动作怎么做
平时积累（无，后台）
产出 / 更新/evolve ← 唯一新增的
装上 / 换版本 / 回滚 / 查看装了哪些宿主自带
命令名是占位，可以改。这里要定的是只有一个新动作，其余全部复用宿主已有的东西。

4 · 还没定的一件事

底层产出一版时，接的是一批材料。那么"这次用哪批"是谁决定的？

  • 自上次产出以来的全部？
  • 按项目分开、各自一直往里追加？
  • 用户自己圈一个范围？

这个决定下来，上面 2.1 那一步的形状才算定死。它是产品决策，不是底层能提供的。

5 · 边界

效果取决于能不能判断对错。

场景
有效跑一下就知道成没成的事：写代码、跑作业、调用有明确契约的接口
无效没有客观判据的事：这段文案好不好、这个设计合不合理

无效的那一类只能靠猜，而我们不猜——不知道就标注不知道。先把窄的做对。
