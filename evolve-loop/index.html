产品定义 · 用户切面

会积累经验的编码助手

助手平时在后台积累学习材料。用户在需要的时候把材料变成一个 mod，装上，之后再更新。

2026-10-03 · 只定义用户切面，实现方案另行讨论

1 · 平时做什么

在每个 turn 的边界上积累学习材料。

一个 turn 开始时记下要做什么，结束时记下做了什么、环境返回了什么、成没成。中间的工具调用、报错和重试都在这些边界上留下痕迹。

全程零打扰：不提问、不弹窗、不要求用户配合。用户应该感觉不到它存在。

这一步没有命令。用户不需要开启、不需要确认、不需要标注。

零打扰是硬约束，不是体验优化。任何需要用户"配合一下"的记录机制，最后都会被关掉。

2 · 用户如何

2.1 指定某个内容，产出一个 mod

用户圈定一段材料——一个项目、一个时间段、一类任务——让助手从中提炼出一个 mod。

产出是可读的：它知道什么、从哪次经历学来的、还不确定什么。不是一团权重。

"指定内容"就是指定一个材料目录。底层只接一个目录，不接时间范围或标签这类过滤条件：

evolve <起点> --learning-material <材料目录>
  → 一个候选目录，里面有它改出来的东西和一份 report.md

起点是一个空白架构（从零开始）。看报告就是读产出目录里的 report.md。

产出不自动生效。

这里有一个产品决策还没做。既然底层只接"一个目录"，那么"我想从最近两周的记录里学"这种需求，必须有东西先把那批材料挑出来、攒成一个目录。谁来挑、按什么挑，是产品要定的，不是底层能提供的。

2.2 安装已有 mod

装上就是把那份经验接到当前会话上。

> /plugin install api-gateway-mod          # 装自己产出的
> /plugin install team-conventions@liquid  # 装别人产出的
> /plugin list                             # 看当前装了哪些

mod 是可分享的。一个项目一个 mod，换项目换一个，互不污染。

2.3 更新 mod

积累了新材料之后，在已有 mod 的基础上再产一版。

更新和产出是同一个动作，区别只在于起点：

evolve <空白架构>   --learning-material <目录>   # 从零：产出第一版
evolve <已有的那版> --learning-material <目录>   # 迭代：在它基础上产下一版

所以不需要一个单独的"更新"命令——把当前这版当起点传进去，就是更新。

更新同样不自动生效：出新版、用户看、用户决定换不换。旧版本身没有被改动过，所以回滚就是继续用它。

三个动作共用一条规矩：产出和更新都只是给用户一个东西看，上线与否永远是人决定的。助手学到的也可能是错的，而一条错误的"经验"会被反复应用，还每次都显得有道理。

3 · 命令一览

底层已经有的两个动作：

动作底层命令产出
产出 / 更新evolve <起点> --learning-material <目录>一个候选目录 + report.md
装上deploy <候选目录> --host <宿主>在宿主上生效

用户切面要做的，是把这两步包成顺手的样子，而不是另造一套语义。包装层需要补的只有三件：

  • 攒材料：把 turn 边界上的记录变成一个合规的材料目录
  • 挑材料：决定这次用哪批（上面那个待定的产品决策）
  • 管版本：候选目录 ↔ 宿主上装着的那版，之间的对应关系
产出物是一个候选目录，不是直接就装好的东西。"产出一个 mod"在底层其实是两步：先 evolve 出候选，人看过之后再 deploy。这个两步结构是刻意的——中间那一步就是人做决定的地方。

4 · 边界

效果取决于能不能判断对错。

场景
有效跑一下就知道成没成的事：写代码、跑作业、调用有明确契约的接口
无效没有客观判据的事：这段文案好不好、这个设计合不合理

无效的那一类只能靠猜，而我们不猜——不知道就标注不知道。先把窄的做对。
