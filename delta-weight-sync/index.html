先解释对象

RL 训练每一步都要把 trainer 的新权重搬进推理引擎

Trainer

Megatron / FSDP / VeOmni

参数分散在几十张卡上（TP/PP/EP/FSDP 各种切法），每步 optimizer 更新后权重变了。

→
Rollout

SGLang / vLLM

按自己的并行方式持有同一模型，负责生成。权重必须与 trainer 保持一致，否则 on-policy 假设被破坏。

核心观察：一步训练后，绝大多数权重字节逐 bit 不变（bf16 实测 ~2–3%，fp8 码域 ~0.1%，MoE ~1%）。全量重发是在搬没变的东西。

Delta weight sync：trainer 侧逐字节 diff，只把变化的位置 + 值发过去，接收端原地写回——难点在"分片坐标系 ↔ HF 坐标系 ↔ 引擎布局"的翻译与逐字节正确性。

Bug #1：server 全程跑在随机权重上

HYBRID 模式下 delta 首次同步只播种快照、不推送权重 → entropy 9.47（≈均匀分布）、grad_norm 0。修复（首次强制全量）后 step1 pearson 0.9994。

Bug #2：NaN 掩码整体失效

HYBRID 的显存腾挪把参数剥离，named_parameters() 从 339 变 0 → "除变化位外全是 NaN"的张量被整体写入。disaggregated 模式下天然不踩（slime 从不踩坑的真正原因）。

教训："输出变了"是假阳性判据——NaN 垃圾也会让输出变（e2e 曾把"Paris. It is the largest city…"写崩成"is is is is…"并当成了成功证据）。此后所有验证以 bit-identity 为准。

6/26–6/29 · 三轮用户纠错后收敛

量化 × delta：可逆性的真正分界线

分界线不是 "fp8 vs nvfp4"

是 "scale 是否纯 per-block、直接存、不折叠、不二次量化"。per-tensor fp8 同样有 max 折叠（用户反问"那个 global scale 在 fp8 不是也会发生吗"戳穿初版说法）。坏的程度：nvfp4 > per-tensor fp8 / int4 > mxfp8 ≈ fp8-block。

nvfp4 的死穴

不是发不过去，而是共享 scale 让 diff 天然稠密：block amax 一变整块 16 值重 round，global amax 一变整张 tensor 重发——"只发变化"的收益直接归零。

生态快照（2026-06-29）：slime 在线 weight-sync 只支持 fp8+int4（nvfp4 掉进 "pass through BF16" 分支）；miles 的 nvfp4 量化器/测试全备但在线未接（PR #1261 OPEN）；slime 已弃 NCCL-delta 转 disk（#2089，quant-then-diff）。值得抄的：astraflow 的 base-version 匹配 + 周期性全量 re-sync。这些判断在一个月后的 fp8 量化域 delta（第十章）里全部兑现。

7/12–7/13 · 17 连败换一个上游 bug

17 连败挖出 upstream 潜伏 bug：zmq PUB/SUB 订阅竞态

机制

订阅注册到 PUB 端是异步的，PUB 对未注册者静默丢消息。32B 时 sglang 启动拖慢传播，seed 4 秒就发首个 manifest → 慢节点 8/16 worker 永久错过 → 三层死锁。7B 一直没炸纯属时序运气；该 bug 潜伏在整个 upstream nccl 引擎家族。

定位与修复

17 个 run：faulthandler 逼栈（rank0 冻在首次 broadcast、其余冻在 FSDP gather）+ 接收侧探针（16/16 进 recv 循环、只有 8/16 收到 manifest）三方拼图。修复 = 无线程 hello/ACK 握手，v17 16/16 全绿。

顺带拿到最硬的反面数据：32B 上不分 shard 的 delta base 稳态 26.1–26.4s——比裸 nccl（23.2s）还慢，而 delta_sharded 是 12.5s。"rank0 全量 gather+diff 的代价吃掉稀疏节省"——sharded 设计的必要性由失败数字坐实。

7/16 · task #8 三轮自我证伪

"delta 到底快在哪"——省的不是传输，是全量重排

假设 1

"15.2GB ÷ 10.1GiB/s ≈ 1.4s，与实测 gap 严丝合缝" → 分段表打脸：发送端等广播只有 0.001s，传输被双缓冲完全藏掉，算术对上纯属巧合。

假设 2

"大量参数一步内完全没动" → pstat 实测：91% 参数每步到场（稀疏只在元素级 ~2%）。"错误的解释比没有解释更糟，这条算我交学费。"

结论

nccl 慢在"物化"：339 次逐参数 all-gather 拼全量、15.2GB 装桶、每桶 cuda sync、逐桶 HTTP——同一个字节被完整读写 6–7 次（60–100GB 显存流量/sync）。delta 每站只按 0.7GB 收费。

书的类比：改了一本 15 万页书里的 700 页。全量 = 整本重印、整本快递、整本重新上架；delta = 只印 / 寄 / 换那 700 页。快递（网线）其实两家都不怎么等——省的是打印和上架的功夫。

追凶链：从 39 个不一致到"+1 个 fp8 码步"

verify 七连击

全量 bit 级 verify 连爆七轮：65KB 日志×3 万次撑爆 ray 512MB、fp8 无 hash kernel、sglang watchdog 300s 悬崖（seed 284.4s 只剩 15.6s 余量——同时结案 1085 个 ActorDied 悬案）……最终拿到真信号：39–57 个 .weight 不一致，100% 集中在需改名/融合的参数。

单张量解剖

layers.0.ffn.experts.85.w3.weight：825,379 个变化位置逐个相同，但 4,654 字节全部 +1 一个 fp8 码步——不是搬运错，是量化错。

根因一号

seed 与 delta 是两个量化器：seed 用 plain（amax/448 直除），delta 用 ue8m0；sglang 源码 format_ue8m0=True 判 seed 错。连 scale 命名都不同。GSM8K 95.3%、probs_diff 1% 全程看不出——生成质量不是正确性判据。

sticky 量化器（用户"trainer 量化时不能按 ckpt 的定义来吗"直接就是最终方案）：ckpt scale 装得下就沿用、装不下才升档。离线 12/12 张量 dequant→requant 逐字节还原；在体 hits=33,346 / misses=0。
