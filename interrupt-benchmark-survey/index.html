Instruct-FD：能否按指令管理轮次

研究问题

全双工系统被明确指示时，能否相应改变其轮次行为。论文指出部署场景的对话策略各异（如主动型辅导 vs 被动型咨询）。

构成

5 类指令 × 29 个场景（proactive 14 + responsive 15）。人工校验的合成 pipeline + deployment-agnostic 多轮评测协议 + LLM judge。

Interrupt 指令模板

Interrupt when {trigger},
listen otherwise

5 类为 Listen / Backchannel / Interrupt / Continue / Acknowledge。

论文给出的 Interrupt 指令实例（原文）

"When the user makes a statement that directly contradicts something they said earlier in the conversation, interrupt immediately to flag the inconsistency…"

具体样例：一个 Interrupt 测试用例

Policy / Instruction

"Interrupt when user say something wrong"

Turn 1 — Context（第一个用户话轮）

"Hey, I'm going to Solve a math problem"

Turn 2 — Trigger（should be interrupted）

"… 2 + 2 equals 5. Given that, The next step is …"

编排方式：orchestrator 只控制用户声道，从不注入模型的回复流；用户与模型音频在同一时间轴上采集。

论文称此设计使所有模型面对相同的流式逻辑、时序结构与用户内容，无需访问模型内部即可公平比较。

Instruct-FD — test case
1 / Instruct-FD

评分标准：IAS 与 ΔIAS

judge 的输入怎么来

用 Qwen3-ASR-1.7B + Qwen3-ForcedAligner-0.6B 取得用户与模型双方音频的词级时间戳；交错两条时间线构造统一转录，并标注重叠区段，得到"何时说了什么"的时间锚定转录。

judge 与流程

judge 模型为 Claude Sonnet 4.6。输入三项：① 该遵循的指令；② 重构转录；③ 由 test case turn logs 导出的 groundtruth 参考。

结构化 CoT 四步：(i) 把指令形式化为规则 → (ii) 构造模型行为的事件时间线 → (iii) 在精确时序约束下评估规则遵循 → (iv) 产出最终判定。

IAS(m, I) = (1 / |D_I|) · Σ_{x∈D_I} 1[ judge(x(I), I) = pass ]

即：对指令 I 的全部测试用例，judge 判 pass 的比例——二值通过率的均值。

ΔIAS(m, I) = IAS(m, I) − IAS(m, ∅ | I)

ΔIAS（Instruction Sensitivity Score）：把不给指令时的响应 x(∅) 同样交给 judge 按指令 I 评判，两者之差即为指令条件化本身带来的行为变化。

论文说明：IAS 高但 ΔIAS 低，说明模型本来就那样做；ΔIAS 高说明对指令响应强。

评分标准：EDS 与打断计数

以下取自发布代码 evaluate/eval_model_interrupt.py（论文对应指标为 EDS）

EDS：judge 评"纠正是否正确且充分"

judge 模型 gpt-4-turbo，temperature=0。输入为「用户的错误陈述」与「AI 的回复」，输出 accuracy_score 与 analysis。

0–5 分，可用 0.5 档：

5 完全正确且全面：关键事实准确、明确指出原错误、给出必要依据、不引入新错误
4 基本正确：主要结论正确且足以解决原错误
3 部分正确：方向对但不完整或有小瑕疵
2 多处不准确：核心纠正有明显错误或缺关键事实
1 大部分错误
0 完全错误，或未作任何事实纠正

EDS = mean(accuracy_score) # 全样本均值
打断的时间判定
input_end = 输入音频最后一个 chunk 的结束时间戳 output_start = 输出音频第一个 chunk 的起始时间戳 duration = output_start − input_end 若 duration < −0.5s → 计为一次打断

即：模型比用户说完早 0.5 秒以上开口，才算一次 mid-speech 打断。代码汇总输出该计数。

代码层面的两点事实

① 200 条 model_interruption 样本均含错误前提，数据中不含 no-error 对照样本。

② EDS 只评回复内容，不含时机项；时机仅由上述 −0.5s 二值判定体现。

MIB：实时纠错的可判定协议

任务

用户口述分步数学解题过程。error 实例中某一步存在计算错误，后续步骤沿该错误继续推导；no-error 实例全程正确。

数据

题目取自 GSM8K，分步解法取自 MR-GSM8K（含步级正确性标注）。从其 incorrect solutions 抽第一个错误步及其错误原因作为 ground truth。

按错误步位置分层：位置 1–5 各 60 条 → 300 条 incorrect，每条配一条同题 correct → 每个评测设定 600 条。

音频合成

用 GPT-5-nano 将解法改写为口语化表述（保留自然度检查得分高者），再由 GPT-4o-mini TTS 合成，流式播放给模型。

论文给出的用户话术模板

"I want to solve this math question. If I make a mistake, please correct me immediately, even when I am still speaking. [question]. Here is my solution: [step-by-step solution]"

MIB — overview
3 / MIB

具体样例（论文 Appendix B 原文）

[Preamble] I want to solve the following math question by myself, and I will let you know how I solve it. If I make a mistake, please correct me immediately, even if I am still speaking and haven't finished my solution.
[2 s silence]
[Question] Here is the question: Sarah's basketball games are 4 quarters that are each 12 minutes long. In the last quarter, there was a tie so the game was extended for five minutes. How long did the entire game last?
[1.5 s silence]
[Answer intro] Here is my answer.
[Step 1] Each quarter is twelve minutes long, so the first three quarters add up to three times twelve equals thirty-six minutes.
[Step 2] The game was extended for five minutes, so the total time for the game is thirty-six plus five equals forty-one minutes.
[Step 3] Therefore, the entire game lasted for forty-one minutes.
[Step 4] So, forty-one.
[Step 5] The answer is: forty-one.

Error reason（原文）

"The calculation of the total time forgot to include the duration of the last quarter itself; the total game time should be 36 + 12 + 5 = 53 minutes."

错误自 Step 2 起，Step 3–5 沿该错误继续推导——模型须在此期间开口。

MIB — instance example
3 / MIB

评分标准：error window + 四分类

error window = [ t_s , t_e + Δ ] Δ = 10 s t_s / t_e = 错误步被说出的起止时间（由 ASR 词级对齐得到） latency(t) = max(0, t − t_e) 仅当 t ∈ [t_s, t_u] 时有定义（t_u = 用户说完） → 打断落在错误步之内 ⇒ latency = 0
TP

在 error window 内正确打断 error 实例

TN

在 no-error 实例上，用户陈述期间保持沉默

FN

未能打断 error 实例，或在窗口内打断但未切中该错误步

FP

在 no-error 实例上打断，或事后声称存在错误

backchannel 不计为打断（如 "mm-hmm"、"right"）；judge 只取第一个非-backchannel 发声，其后的发声一律忽略。

judge 模型为 GPT-5.2（gpt-5.2-2025-12-11），确定性解码 temperature = 0，回复缓存以保证可复现。模型输出先经 ASR 取词级时间戳。

ProVoice-Bench：主动性的四类任务

上海交大 · 1,182 条样本 · 四类任务

PIC

Proactive Intent Capture

从细微语言线索（如犹豫、对话中提及的待办）推断隐含意图，主动发起 tool-call 并寻求确认。

LTM

Latent Topic Monitor

用户指示模型监听环境对话；模型保持沉默，仅在检测到用户指定的触发时介入。

CFC

Context Fact Checking

当口头陈述与用户手机上的数字上下文相矛盾时，主动打断并给出事实纠正。

ESS

Environment Sound Sensing

在识别到特定声学事件（如警报）时提供协助，在此之前保持沉默。

样本形式化（原文）

每条样本 = 五元组 (C_a, D_c, S_c, R_g, T_g)

C_a 对话音频 · D_c 用户数字上下文 · S_c 语义线索（指示触发主动交互的对话背景与关键信号）· R_g 参考文本回复 · T_g 参考 tool-call。

ProVoice-Bench — CFC example
4 / ProVoice-Bench

评分标准：两层

① Proactive Interaction Prediction

评估模型判断是否需要介入的能力：

Accuracy (Acc) — 整体二元决策表现
False Positive Rate (FPR) — 在不存在有效触发时不必要介入的频率
Recall (Rec) — 识别真实交互触发的敏感度

该层含负例（无有效触发的样本），故可测 FPR。

② Response Accuracy (R_acc)

在触发判断之外，进一步评估后续动作的正确性：

S_i = [ J(S_c,i, T_p,i, T_g,i) + J(S_c,i, R_p,i, R_g,i) ] / 2 · I( pred_i = gt_i )

J(·) ∈ {0, 0.5, 1.0} 为 LLM-as-a-Judge，以语义线索 S_c 为评判上下文，评估预测输出相对 ground truth 的功能合理性与对齐度；judge 模型为 Qwen3-80B。

T 为 tool-call 序列、R 为文本回复（p 预测 / g 参考）；I(·) 为指示函数，模型决策与 ground truth 一致时取 1。

即：触发判断错则整条 S_i 归零；判断正确时，得分为 tool-call 与文本回复两项 judge 分的均值。

论文报告中，各模型 FPR 差异极大——例如 Step-Audio-R1 在 CFC 上 FPR = 0.961，而 Qwen3-Omni(T) 为 0.061（Rec = 0.737）。
