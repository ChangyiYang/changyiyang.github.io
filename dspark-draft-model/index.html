三层度量
Architecture

drafter 长什么样，以及我们关掉的那个头

参数分布（3L 共 231.2M）

backbone（3 层）144.7M / 63%
Markov 转移头 65.5M / 28%
输入 fc 21.0M / 9%
confidence 头 2,305

没有 embedding / lm_head，直接共用 target 的。纯 full-attention。

接受判据（读源码核对过）

draft 一次提 block_size=7 个 token，target 一次前向验证 8 个位置。

接受判据是标准 rejection sampling coin·q < p，即 min(1, p/q)；p 与 q 索引对齐，温度两边同源且各只应用一次。

⚠️ 我们没有训 confidence head

它本来干嘛的：预测每个 draft token 会不会被接受，让服务端在没把握时提前终止整个 block。
代价：compact / cap-accept 两种 verify 模式会从 checkpoint 加载它，所以我们只能跑 static——而 clawenv harness 默认就是 compact，第一次跑 verl 时就是这么崩的。
但实测没吃亏：同权重 static vs compact，accept length 只差 −0.18，而 compact 吞吐明显更差（77 vs 126 tok/s）、端到端更慢。static 本来就是该用的模式。
唯一真损失：serving 侧"每步接受几个 token"的直方图被同一个开关挡住了，而那正是定 block_size 的直接依据。

drafter 结构
Data & training

语料、配方，和两个反直觉的地方

语料

harvest-1 22.4M 监督 token（2,824 条）→ v2 117M（14,838 条），扩了 5.2×。

但监督密度只有 12.8%（公开参考语料 81.4%）——agentic 轨迹里大部分是工具返回。比语料要比"监督 token"，不是"记录条数"。

配方

eff_bs 128 · lr 4.243e-4 · 20 epoch · block 7 · 每条 record 每 epoch 采 512 个 anchor。

W&B：liquid-lfm-dspark/runs/gxlzenul（3L）、9run8fc4（5L）、liquid-lfm-dflash/runs/xo3kthsv（DFlash）。

反直觉 ①：旧版 lr 高了 2.8×

规则是 lr = 6e-4·sqrt(eff_bs/256)。旧版直接用 6e-4，但它的 eff_bs 只有 32——按规则应是 2.1e-4。

所以旧 baseline 的 tau 3.71 里，多少是语料、多少是被 lr 拖累的，其实分不清。

反直觉 ②："训了 20 epoch" ≠ "记住了"

每条 record 约 7,910 个可监督位置，每 epoch 只采 512 个 anchor：

(1 − 512/7910)20 = 0.262

"见过"的样本里 26% 的位置从没被训练过，中位数位置只被监督约 1.3 次。

为什么尾部比看起来重要

accept length 是累乘：1 + Σ cumprod(acc_pk)。所以尾部塌一点，整条乘积就塌下去。

DSpark 3L 里位置 4-6 贡献了 0.40——接近总量的三分之一。

tau 的两个陷阱

① tau 是逐 block 算完再平均，所以 1 + Σ mean(ar_pk) 复现不出来（E[Πx] ≠ ΠE[x]）——我们踩过：反推 2.339，真实 1.801。

② tau 是 teacher-forced 的，结构性地看不见只在服务时发生的问题（如 rope_theta 不匹配）。

推论：sglang 4.67 vs rollout 3.37 的差距是流量，不是并发

所以想提升 rollout 的 accept length，得让训练数据贴近模型自己漂移后的状态（Draft-OPD 路线），调并发没用。

这层的吞吐读不出来：各 arm 生成量差 25%，固定 record 数的墙钟把"速度"和"内容多少"混在一起，按 token 归一后排序还和 accept length 矛盾。

为什么高并发不赚？按主流说法它本不该这样

机械上：一个 DSpark step 吐 accept_len 个 token，但要花 draft 的 7 次串行前向 + target 对 8 个位置的一次前向。低并发时 target 前向被显存带宽卡住，验 8 个位置几乎白送；高并发时算力饱和，就是实打实约 8 倍。

但这套说法解释不了 DSpark 本身——按目前比较 common 的认知，DSpark 在大 batch 下也不该掉 throughput（见下图 lmsys 的对比）。所以我们在 rollout 上测不出收益，更可能是 AMD 上的 DSpark 实现还不够好，而不是这个技术的固有性质。Piotr 正在看这件事。

我们目前只有两个端点——并发 1（赚 1.11-1.33×）和 rollout 并发（不赚），中间的曲线还没测。后续会对线上真实流量做 bsz 相关的 profile，把这条曲线补上。

Serving stack

接受判据正确

确认是标准 min(1, p/q)；p 与 q 索引对齐，block 7 / 8 token 没有越界；温度两边同源、各只应用一次。

rope_theta：机制是真的，幅度被我高估了

draft 的 rope_theta 必须等于 target 的。训练侧看不见——draft 自己建 KV，两边自洽，tau 完全正常；服务时 draft 复用 target 的 KV，不匹配才暴露。

同权重 A/B 实测：匹配比不匹配高 +0.46（约 1.4σ），而且另一个 arm 反而略低。最初报的 "+75%" 是在一套有缺陷的 prompt 上量的，已收回。

DFlash 对照
Lessons

四个发出去又收回的结论，全是口径问题

prompt 切在 JSON 中间

按固定 token 偏移切 prompt，切点落在 "author": "j 这种地方，模型接的是被截断的乱码。造出一个假的性能回退：1.3 vs 2.44。

修法：用 supervision mask 的 0→非零跳变，切在 assistant 轮次开头。

spec 环境变量泄漏给 baseline

把 SGLANG_RAGGED_VERIFY_MODE 等写在共享的 --export 里，不开投机的 baseline 也吃到了，结果它吐出 <think> + 512 个换行、永不终止。

分母被污染，造出一个假的 1.79× 加速。对照臂复现后确认：24/24 全部跑飞。

固定 record 数当吞吐测

各 arm 生成量差 25%，墙钟同时混进"速度"和"内容多少"。我据此报过 1.21× 慢，后来收回。

rope_theta "+75%"

在有缺陷的 prompt 集上量的，真实只有 +0.46（约 1.4σ）。机制成立，幅度不成立。

两条可迁移的规矩：① 报数字必须带口径（温度 / 并发 / 截断长度 / 样本数）；② 花卡之前先确认"这个判据真的能被观测到"——我们有五次 e2e 跑完 exit 0 却什么都没测到。

下一步，按性价比排序

1 · 并发扫描（1/2/4/8/16/32）

把"随并发失效"从两个端点补成完整曲线，并直接读出我们自己 target 上的收支平衡并发。不用重训，约 40 分钟。

2 · block_size 扫描 7 → 4/3/2

压每步成本最直接的抓手。逐位置曲线显示位置 4-6 只贡献 0.40，砍短很可能划算。不用重训。

3 · 暴露 num_correct_drafts 直方图

约 15 行改动，补上"每步接受几个"的分布——定 block_size 的直接依据。

4 · 用漂移后的 rollout 状态训练

按并发分析，这是提升 rollout accept length 唯一的抓手（Draft-OPD 路线）。

一句话总结

drafter 不是瓶颈——同栈可比参照的 accept length 是 3.65-3.99，我们 5L 是 3.707（rollout）/ 4.79（并发 1），持平甚至略高。
瓶颈是高并发下每个 DSpark step 的成本。所以下一步该压成本（并发扫描、block_size），而不是继续堆 drafter。
